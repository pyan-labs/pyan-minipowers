# spec-design에 암묵지를 끌어내는 인터뷰(grill-me)를 보강한다

2026-10-04 외부 리뷰의 다섯째 todo다. 01~03과 독립이다. [04](2026-10-04-04-index-decision-summary.md)와는 spec-template을 함께 건드리므로 04 뒤에 한다.

## 현상

- spec-design의 순서는 3절 코드 읽기 → 4절 초안 쓰기 → 5절 전제 확인 → 6절 사용자에게 묻기 → 7절 검토 요청이다.
- 6절은 "코드가 답해 주지 않는 결정만" 묻는다. 묻는 것은 초안을 쓰다가 모델이 스스로 빈칸이라고 느낀 곳이다.
- 그래서 두 가지가 빠진다.
  - 모델이 빈칸인 줄 모르는 것. 운영에서 실제로 쓰는 방식, 예전에 해 보고 접은 방법, 고객과의 약속, 데이터의 예외처럼 코드에 없고 사용자 머리에만 있는 것이다. superpowers의 brainstorming을 grill-me 방식으로 쓰던 이유가 이것이었다.
  - 모델이 묻지 않고 스스로 정한 것. spec "결정"에 사용자가 정한 것과 모델이 채운 것이 구분 없이 섞여, 7절 검토에서 사용자가 어느 줄을 의심해야 할지 알 수 없다.
- 초안을 먼저 쓰므로 이후 질문이 초안을 확인하는 쪽으로 기운다.
- 반대쪽 비용도 있다. 기능 20개마다 긴 인터뷰를 하면 피로하다(9월 26일에 정리한 문제의식).

## 결정할 것

1. **인터뷰의 위치.** 추천은 3절(코드 읽기) 뒤, 4절(초안) 앞이다. 코드를 읽은 뒤라 코드로 답이 나오는 것은 묻지 않고, 초안 전이라 초안에 끌려가지 않는다.
2. **묻는 각도.** 추천은 고정된 각도 목록을 두고, 각도마다 코드와 todo에서 읽은 것을 근거로 질문을 만드는 것이다. 목록 초안은 다음이다.
   - 왜 지금인가: 이 요구가 나온 실제 사건과 누가 불편했는지. 대개 todo 원문(승인 뒤 `<stem>/todo.md`)에 답이 있으므로 그 답을 추정으로 먼저 보인다
   - 실제 사용: 화면이나 기능을 현장에서 쓰는 순서, 코드와 다르게 쓰는 관행
   - 예외와 데이터: 정상 흐름을 벗어나는 경우, 과거 데이터의 특이점
   - 과거의 시도: 전에 해 보고 접은 방법과 접은 이유
   - 건드리면 안 되는 것: 겉보기에 고칠 만하지만 그대로 둬야 하는 것과 이유
   - 끝난 모습: 무엇을 보면 됐다고 할 것인지, 누가 확인하는지
3. **끝내는 조건.** 추천은 관찰 가능한 조건 둘이다. 사용자가 "충분"이라고 하거나, "인터뷰" 표(결정 6)의 모든 각도에 답이 적혔고 남은 질문이 없다. 질문 수 상한은 두지 않는다(AGENTS.md "숫자 상한으로 갈리지 않게").
4. **피로 줄이기.** 질문을 하나씩만 하면 한 줄짜리 변경도 각도 수만큼 왕복한다. 추천은 두 단계로 묻는 것이다.
   - **1단계: 각도 일괄 확인.** 첫 메시지에 모든 각도를 한꺼번에 보이고, 각도마다 코드·todo·이전 digest·"이후 작업에도 적용되는 결정"(04)에서 읽은 근거와 추정 답을 붙인다. 사용자는 각도마다 "맞다 / 해당 없음 / 고친다"로 답한다. 이전 작업에 답이 있는 각도는 그 답을 인용하고 "지금도 같은가"로 묻는다.
   - **2단계: 고친 각도만 파고들기.** 사용자가 "고친다"로 답한 각도만 질문 하나씩, 근거와 추천 답을 붙여 묻는다(지금 6절과 같은 방식).
   - 작은 변경은 1단계 한 번 왕복으로 끝난다.
5. **모델이 스스로 정한 것의 표시.** 후보는 다음이다.
   - (a) spec "결정 › 바꾸는 것"의 번호마다 끝에 `(사용자 결정)` 또는 `(추정)`을 붙인다.
   - (b) 7절 검토 요청 메시지에만 "묻지 않고 정한 것" 목록을 적는다. spec에는 남지 않는다.
   추천은 (a)다. 뒤 단계와 digest의 독자도 어느 결정이 사람의 것인지 알 수 있고, spec-review가 `(추정)`이 붙은 결정의 구현을 더 볼 근거가 된다. 줄 형식이 계약에 더해진다.
   - 의미를 정해 둔다. 승인은 spec 전체를 승인하는 것이라 그것만으로 `(추정)`이 지워지지 않는다. `(추정)`은 "사용자가 개별로 확인하지 않은 결정"이다. 인터뷰 답이나 검토 중 사용자가 그 결정을 짚어 확인했으면 `(사용자 결정)`으로 바꾼다.
6. **인터뷰 기록을 어디에 남길지.** 답의 본문은 기존 절에 나눠 적는다. 실제 사용과 예외는 "문제 › 현상 · 배경"과 "구현 맥락"에, 과거의 시도는 "기각한 대안"에, 건드리면 안 되는 것은 "바꾸지 않는 것"과 "리뷰 기준"에, 끝난 모습은 "수용 기준"에 간다. 사용자의 말은 가능한 한 원문으로 인용한다.
   - 그것만으로는 어느 각도를 이미 물었는지가 관찰되지 않는다. 특히 "해당 없음"은 흔적이 남지 않아, 끊긴 세션을 이어받은 모델이 다시 묻게 된다.
   - 추천은 spec에 짧은 `## 인터뷰` 절을 더하는 것이다. 표 한 개로 `| 각도 | 답 요지 또는 "해당 없음" | 옮겨 적은 절 |`이다. 이 표가 이어받기 상태이고, 결정 5의 `(사용자 결정)` 표시의 근거이며, digest 독자에게 어느 맥락이 사람에게서 나왔는지 보인다. 뒤 단계는 이 절을 읽지 않아도 되므로 계약 부담이 작다.
   - 기각 후보: 표를 `.minipowers/<stem>/interview.md`에 일회용으로 둔다. 이어받기는 되지만 기록이 남지 않는다.

## fix plan (결정 뒤)

1. `spec-design/SKILL.md`에 3절과 4절 사이에 "인터뷰" 절을 넣고 뒤 절 번호를 민다. 다른 문서와 SKILL.md 안에서 번호로 가리키는 곳(conventions.md의 "spec-design/SKILL.md 8절", "3절", SKILL.md 1절의 "2절의 2", "5절부터", 8절 안의 단계 번호 참조)을 함께 고친다. 번호 대신 절 제목으로 가리키게 바꾸는 것도 이때 한다.
2. 인터뷰 절에는 목적("코드에 없고 사용자만 아는 것을 초안 전에 끌어낸다"), 각도 목록, 질문 방식(결정 4의 두 단계), 끝내는 조건, 답을 옮겨 적을 절을 쓴다. 절차를 길게 늘어놓지 않는다.
3. 지금의 6절 "사용자에게 묻기"는 초안을 쓰다가 생긴 결정 질문으로 남긴다. 인터뷰에서 이미 답한 것은 다시 묻지 않는다.
4. (결정 5가 (a)이면) `spec-template.md` "바꾸는 것"에 표시 규칙과 `(추정)`의 의미를 더하고, 7절 검토 요청에 `(추정)` 결정 목록을 넣는다. 검토 중 사용자가 짚어 확인한 결정은 `(사용자 결정)`으로 바꾼다. `spec-review/SKILL.md` "읽는 순서"에 `(추정)` 결정을 리뷰 기준 대조에 포함한다는 한 줄을 더한다.
5. 끊긴 세션 이어받기(1절 예외): 인터뷰 중에 끊기면 초안 파일이 아직 없다. 인터뷰를 시작할 때 머리말, "원 요구", 빈 `## 인터뷰` 표만 채운 초안을 먼저 쓴다. 답을 받을 때마다 표의 행과 해당 절을 적는다. 이어받을 때는 `## 인터뷰` 표에 답이 없는 각도부터 묻고, 모든 각도에 답이 있으면 초안 쓰기로 간다. `spec-template.md`에 `## 인터뷰` 절을 더한다.
6. README 두 언어의 Design 행과 "Decisions end at the design stage" 문단에 인터뷰를 한 줄로 더한다.

## 검증

- 실제 프로젝트의 todo 하나로 `/spec-design`을 5.14.0과 바꾼 버전에서 각각 돌려 두 spec을 비교한다. 볼 것은 "바꾸지 않는 것", "기각한 대안", "리뷰 기준"에 코드에서 나올 수 없는 내용이 몇 줄 늘었는지와, 질문 수와 걸린 시간이다.
- 이전 작업이 있는 저장소에서 돌려, 이미 답이 있는 각도를 인용으로 넘기는지 본다.
- 인터뷰 중간에 세션을 끊고 `/spec-design docs/minipowers/<stem>/`으로 이어받아, 답한 각도를 다시 묻지 않는지 본다.
- 한 줄짜리 작은 변경에서 인터뷰가 1단계 한 번 왕복으로 끝나는지 본다.
- 인터뷰 중 "해당 없음"으로 넘긴 각도가 이어받은 세션에서 다시 묻히지 않는지 본다.
